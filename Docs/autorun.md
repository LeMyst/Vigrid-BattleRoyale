# Auto-run (`Extra/AutoRun/`)

> Split out of the root [`CLAUDE.md`](../CLAUDE.md), which carries the build, test and EnfusionScript rules every change needs - read that first. A correction made here must also reach the memories and skills that repeat the rule (see *Workflow* in `CLAUDE.md`).

A standalone auto-run replacing DayZ Expansion's, one of the features that goes with the Expansion dependency. Builds into `extra_autorun.pbo` and defines `VIGRID_AUTORUN`. Hooks vanilla only, so it works on any DayZ server. **Same discipline rule** as `Party/`, `Extra/KillFeed/`, `Extra/SafeZone/` and `Extra/Map/`: nothing under it may reference a `BattleRoyale*` symbol — own logger (`VigridAutoRunLog`, CLI flags `-autorun-*`, `serverDZ.cfg` key `AutoRunLogLevel`), own `stringtable.csv` (`STR_AUTORUN_*`), own `Data/Inputs.xml`, own RPC namespace (`RPC-VigridAutoRun-Server`, message `VA_SetSpeed`). No settings file at all.

**The bind is `Z`, and `X` was ruled out on inspection.** `kX` is vanilla `UAToggleWeapons` — change firearm fire mode, consumed at `P:\scripts\5_mission\mission\missiongameplay.c:551` — so a bind there fires twice per press. `kZ`'s only vanilla binding is `UAMoveDown`, under the preset's *DEBUG SPECIFIC / Freefly Camera* block, unreachable in normal gameplay; Expansion's own auto-run defaulted to it. ⚠️ **Free letters are nearly gone**: `K`, `O` and `P` are the only ones vanilla leaves unbound, and Map has `K`, Party has `P`. The next addon that wants a letter has exactly one left.

⚠️ **While Expansion is still in the load order, `Z` drives both auto-runs** — matching Expansion's default is deliberate (muscle memory survives the migration) but one press engages both and their cancel rules fight. Rebind Expansion's, or set its `EnableAutoRun` to 0, until the dependency is actually gone. Confirmed live 2026-08-16: rebinding Expansion's key made the feature behave correctly.

**The mechanism is `HumanInputController.OverrideMovementSpeed` / `OverrideMovementAngle` held at `ENABLED`** (`P:\scripts\3_game\human.c:234-237`) — the same pair `PlayerBase.DisableInput` already uses with a speed of `0` to freeze players, which is both the reference for the call shape and the source of every interaction problem below. Speed is **adopted** from `hic.GetMovement()` at the press (sprint stays sprint, walk stays walk), and a requested sprint is held at a run while `LimitsIsSprintDisabled()` is true — that flag un-latches by itself, so "sprints again once rested" is free. **Standing still is the only case that reads `UATurbo` directly**: Shift + the bind sets off at a sprint, the bind alone at a run. The moving cases need no modifier check because the modifier is already folded into `GetMovement` — Shift + W reports a `3`.

Five things are load-bearing:

- ⚠️ **The override is applied on BOTH sides**, client locally plus an edge-triggered client→server RPC carrying the resolved speed. Vanilla's own `RPC_DAYZPLAYER_DEBUGSERVERWALK` (`P:\scripts\4_world\entities\dayzplayerimplement.c:3723-3733`) is exactly this — a client→server message whose whole body is `OverrideMovementSpeed` on the server's copy of the player — and Expansion synced it too. **Whether the client half alone would have sufficed is untested**; the server-side Debug line on start/stop is what would answer it.
- ⚠️ **`VigridAutoRunState` keeps a per-uid record of whose override the addon owns, and that record is not bookkeeping — it stops a real race.** If a client's "auto-run off" lands *after* a host freeze, a handler that simply passed `DISABLED` would **release the freeze** and hand a frozen player their controls back, silently. A release only ever happens for a uid still on the record, and `VigridAutoRunAPI.CancelFor` drops the record **without touching the controller**, because the host is about to write its own override on the very next line. Call order is therefore load-bearing: cancel first, freeze second.
- **The cancel-on-movement test needs an arming latch.** The natural way to start auto-run is to press the bind *while running*, so W is still held on that frame; without `m_CancelArmed` — set on the first frame with nothing held — the feature cancels itself instantly and appears to do nothing at all. A stance change cancels (it is a press event, no latch needed); a **jump deliberately does not**.
- **The feature lives in 4_World, not beside its `MissionGameplay` glue.** `VigridAutoRunAPI` has to be 4_World so a host mod's *server states* can reach it, and a 4_World class cannot name a 5_Mission type. Same shape as Party: state low, renderer high. `AutoRunMissionGameplay` is the **5th** shipping `modded class MissionGameplay` and is glue only.
- ✅ **`VIGRID_AUTORUN_MOVEMENT_ANGLE = 0` is correct, measured 2026-08-16** — the character runs straight ahead. Worth recording because the alternative reads better than it is: `0` is what `DisableInput` passes and is the obvious "no deviation", but vanilla's own call sites pass `1`, both the AI bot (`bot_hunt.c:145`) and the camera tools (`ctevent.c:50`), with no documented unit anywhere. **Do not "fix" it to 1.** It stays a named constant so a future regression is still a one-variable experiment.

Two call sites in the mod, each `#ifdef VIGRID_AUTORUN`: `BattleRoyaleClient` where it applies the `SetInput` RPC calls `SetAllowed( !input_state )` (which also cancels a hold in progress, so there is no separate client cancel), and `4_BattleRoyalePrepare.DisablePlayerInput` calls `CancelFor(player)` on the line above the freeze.

✅ **Vanilla's walk pin does not reach the movement override, measured 2026-08-16 — so there is deliberately NO `AddActiveInputRestriction` override in `AutoRunMissionGameplay`.** Vanilla's entire body for the `INVENTORY` and `MAP` restrictors is `UAWalkRunForced.ForceEnable(true)` — *"force walk on!"* (`missiongameplay.c:1001-1024`) — which is what walks a player who opens their inventory. Read on its own that says auto-run's speed must halve, and a build shipped an override countering it; `OverrideMovementSpeed` sits downstream of the pin and an auto-running sprint stays a sprint. **It was deleted rather than kept "just in case"**, and that reasoning generalises: a no-op guarded on `IsActive()` is indistinguishable from a working one, so keeping it would have made it read as load-bearing forever. The absence is documented in the file itself so nobody re-adds it from the same reading of the sources.
